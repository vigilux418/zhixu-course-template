用更小的问题，回答大问题

前两讲里，我们都在追问“怎样更快”。这一讲换个角度：怎样把一个暂时不会做的大问题，换成一个更小、但同样类型的问题？递归（recursion）把这种拆解直接写进代码，也把“边界”这件事摆到了最显眼的位置。

  • 识别“长得一样”的子问题
  • 写出一定能停下来的递归
  • 看懂调用栈的展开与返回
  • 分清递归的代价与适用场景

让问题保留原来的模样

非负整数 n 的阶乘，记作 n!。n 不小于 1 时，它是从 1 乘到 n 的连乘；0 没有什么可乘的，约定 0! = 1。举个例子：5! = 5 \times 4 \times 3 \times 2 \times 1 = 120。这个连乘有个容易被忽略的性质——去掉开头的 5，剩下的 4 \times 3 \times 2 \times 1 恰好就是 4!。

n! = n \times (n - 1)!

想求 n 的阶乘，先求 n - 1 的阶乘，再乘上 n。问题变小了，形状却没变。

沿着一路走下去：5! 需要 4!，4! 需要 3!，3! 需要 2!，2! 需要 1!。到 1! 时不必再拆，因为 1! = 1 是已知的（0! = 1 同样是约定好的）。这个“不用再拆”的地方，就是递归（recursion）的终止条件（base case）。

换个角度看：递归把一条长长的连乘，拆成一串“我做一小步，剩下的交给下一层”的接力。每一层只负责自己那次乘法，其余的相信下一层会给出答案。

  1. 原问题求 3 的阶乘
  2. 子问题先求 2 的阶乘
  3. 组合3 乘以子问题的答案

把答案一层层接回来的前提是：每一层都比上一层更靠近终点，递归才停得下来。

递归的两个关键

写递归时，只要先回答两个问题，代码的骨架就出来了。

什么时候不再拆？
终止条件：n 为 0 或 1 时直接返回 1。没有它，递归会一直往下调用，直到程序崩溃。
怎么让问题变小？
递归步骤：把 n! 写成 n 乘以 (n - 1)!，每次调用都让参数减一，稳定地靠近终止条件。

把两个回答合在一起，就是阶乘的完整定义：

n! = \begin{cases} 1, & n \le 1 \\ n \times (n - 1)!, & n \gt 1 \end{cases}

一句话记住递归的两半：一个缩小的动作，一条守得住的边界。只有动作没有边界，会停不下来；只有边界没有动作，问题永远原地打转。

两者还要配合：边界给出终点，缩小的动作保证每一层都在朝终点迈进。判断一段递归写得对不对，先看这两件事，通常比从头读一遍代码更快。

写成函数，只有几行

把上面两句话翻译成代码。注意它同时包含“向下调用”和“向上返回”：必须先拿到 factorial(n - 1) 的结果，当前这一层的乘法才能完成。下面同样是 Python 与 JavaScript 两版，逻辑一字不差。

def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(5))  # 120
print(factorial(0))  # 1
  1. 终止条件：命中边界就直接返回，不再向下调用。
  2. 递归步骤：先让下一层算出 (n - 1)!，再乘上 n。
function factorial(n) {
  if (n <= 1) {
    return 1;
  }
  return n * factorial(n - 1);
}

console.log(factorial(5)); // 120
console.log(factorial(0)); // 1
  1. 终止条件：命中边界就直接返回。
  2. 递归步骤：调用参数小一号的自己。

为了看清结构，两版都省略了类型检查；实际使用时，应当先确认 n 是非负整数。

代码里最容易被误读的是 factorial(n - 1) 这一句：它不是“稍后再算”，而是真的暂停当前这一层、进入下一层，直到最底层交回一个具体的数，才开始一层层往回乘。

沿着调用，再走回来

以 factorial(3) 为例，把整个往返过程画出来，会清楚很多。

向下时，三层调用叠在一起，谁也没有算出结果；factorial(1) 直接返回 1 之后，计算才开始“倒着”发生：2 \times 1 = 2，3 \times 2 = 6。这种后进先出的结构，就是调用栈（call stack）。

换个比喻：把每一层调用想象成往桌上叠一张卡片，最后放上去的，最先被拿走。栈顶永远是正在执行的那一层，压在下面的都在等它；而 6 这个最终答案，要等所有卡片都被取走之后，才出现在桌面中央。

递归的答案，是回来的时候才凑齐的。向下走，是为了找到那个可以开始的地方。

递归的代价，和它的用武之地

递归让代码更接近定义，但它不免费。每向下调用一层，语言都要在调用栈上保存这一层的位置与局部变量；层数越深，占用越多，而调用栈的大小是有限的。Python 干脆给递归深度定了一个上限默认是 1000 层，可以用 sys.getrecursionlimit() 查看。，超过就报错；C、Java 这类语言不规定层数，但栈用完了同样会出错。

永远到不了终止条件的递归不会“慢慢算”，而是直接失败：Python 抛出 RecursionError，JavaScript 报告调用栈溢出；在 C 这类语言里，栈被耗尽之后程序通常直接崩溃。

所以直白的阶乘，用循环写往往更省内存；而像文件目录遍历、树形结构的遍历这类“结构本身就是嵌套”的问题，递归反而更自然——它和问题的形状对上了。先看阶乘的两种写法：

def factorial(n):
    if n <= 1:
        return 1
    return n * factorial(n - 1)
def factorial(n):
    result = 1
    for k in range(2, n + 1):
        result *= k
    return result

两种写法结果相同：递归版要叠起 n 层调用，循环版自始至终只用一个变量记录乘积。再看一个结构本身就嵌套的问题。

用嵌套列表表示一个文件夹：数字是文件的大小，列表是子文件夹。下面的函数计算总大小。

def total_size(item):
    if isinstance(item, int):
        return item
    return sum(total_size(child) for child in item)

print(total_size([120, [40, [8, 2]], 30]))

它的终止条件和递归步骤分别在哪几行？最后一行会打印什么？

解答

终止条件是第 2–3 行：遇到文件（一个数字）就直接返回它的大小。递归步骤是第 4 行：文件夹的大小等于其中每一项的大小之和，而每一项又交给 total_size 自己去算。打印结果是 120 + 40 + 8 + 2 + 30 = 200。

文件夹嵌套多少层，这段代码都不用改；换成循环来写，就得自己维护一份“还没处理的文件夹”清单。

反过来，写错的递归通常错在两个关键之一。下面三种写法各会发生什么？先想一想，再点开。

如果把递归步骤写成 factorial(n) 而不是 factorial(n - 1)，会发生什么？

每一层调用的问题都没有变小，永远到不了 n <= 1 这条边界。程序会不断向下调用，直到调用栈被耗尽，抛出类似“递归深度超出限制”的错误。这提醒我们：边界写得对还不够，每次调用都必须真的朝边界移动。

如果删掉终止条件，只留下递归步骤呢？

参数会一路减下去：1、0、−1、−2……没有任何一层肯直接给出答案，结果同样是调用栈耗尽。缩小的动作还在，却没有边界接住它。

如果终止条件写成 n == 1，再调用 factorial(0) 呢？

0 不等于 1，于是继续调用 factorial(-1)、factorial(-2)……参数离 1 越来越远。边界存在，却没有覆盖所有可能到达的输入；写成 n <= 1 才守得住。

递归与数学归纳法是同一套思路的两种写法：边界情况对应归纳的起点，递归步骤对应“假设小一号的问题成立，推出当前问题也成立”。能读懂归纳证明的人，通常很快就能读懂递归。

第一讲用循环不变式说明找最大值为什么正确（），用的也是这种“从起点一步步推到终点”的推理。

检查你的理解

要让这一讲的递归一定能停下来，必要的是哪一条？

  1. 只要写了终止条件就行，参数怎么变化无所谓
  2. 有明确的终止条件，并且每次调用都更接近它
  3. 递归的层数不超过语言允许的上限

递归要能正常结束，需要两件事同时成立：有可以直接回答的终止条件，并且每次递归调用都让问题更接近这个终止条件。少任何一条，递归都无法收敛。只写终止条件不够：上一节的反例里边界还在，参数却离它越来越远。层数的上限只管出错时报错，不能让递归自己停下来。

按本讲的写法调用 factorial(4)，factorial 这个函数一共被调用了几次（含最外层这一次）？

从 factorial(4) 开始，一层层写到命中边界为止。

依次是 factorial(4)、factorial(3)、factorial(2)、factorial(1)，共 4 次；到 factorial(1) 命中边界，不再向下调用。

不运行代码，写出 factorial(4) 向下调用与向上返回的全过程，再对照解析。

向下：factorial(4) 等 factorial(3)，factorial(3) 等 factorial(2)，factorial(2) 等 factorial(1)。向上：factorial(1) 返回 1，接着是 2 \times 1 = 2、3 \times 2 = 6、4 \times 6 = 24。如果你写下的顺序与此一致，说明已经看懂了。

本讲小结

  • 递归把问题拆成一个更小的同类问题，再用它的答案拼出当前答案。
  • 终止条件给出终点，缩小的动作保证每一层都在靠近它，两者缺一不可。
  • 调用栈后进先出：向下时层层等待，触到边界后才逐层返回。
  • 递归有栈深度与内存成本；结构自嵌套的问题用它更自然，简单重复则未必。
