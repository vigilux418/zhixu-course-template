当问题变大，会发生什么

前一讲我们算过：二分查找最多 11 次，顺序查找最坏 1024 次。但“11 比 1024 小”只是对某一组数据成立的观察。如果数据变成 100 万条，这个比例会保持、缩小还是拉大？要回答这个问题，得换一把尺子。

  • 区分实际耗时与增长趋势
  • 读懂 O(1)、O(log n)、O(n)、O(n²)
  • 用最坏情况比较两种查找
  • 知道复杂度理论的来路

先数操作，再看增长

上一讲比较了两种查找：顺序查找最坏要看遍每一个元素，二分查找每次砍掉一半。我们真正想知道的，是当问题规模继续变大，这种差距会缩小、维持，还是拉大。

同一段程序，在老笔记本上跑 2 秒，在服务器上只要 0.2 秒；只盯着“秒”，很容易得出错误的结论。为了把“机器有多快”从讨论里拿掉，我们换一个计量单位：不数秒，数基本操作执行了多少次。找最大值时，基本操作是“比较两个数”，n 个数需要比较 n - 1 次；二分查找里，基本操作是“比较一次中点”，每比一次，候选范围就减半。机器快慢只会改变每秒能做多少次操作，不会改变操作次数随规模增长的方式——而后者，恰恰决定了数据变大之后这个方法还能不能用。

重要的不只是现在有多快，还有规模翻十倍之后，还站不站得住。时间复杂度讨论的正是这件事。

把“几秒”换成“几次操作”，是为了剔除机器差异，只留下可以推理、可以互相比较的部分。这也解释了为什么两台性能悬殊的电脑上，比较两个算法的结论常常一致。

把三种增长画在同一张图上

横轴是问题规模 n，纵轴是基本操作次数。把常见的几种增长叠在一起，差别立刻显形。

读时记住三件事：曲线的高低不代表绝对耗时，它只描述增长方式；起点附近的差距说明不了什么，规模很小时，系数和低阶项的影响很大；规模越大，曲线之间张得越开。当 n = 1000 时，\log_2 n 约为 10，n 是 1000，n^2 已达 1,000,000——同一台机器上，这三者已经不是“快一点”和“慢一点”的关系。

花哨的算法在 n 很小时很慢，而 n 通常很小。

Rob Pike，《Notes on Programming in C》，1989

这句来自工程师的提醒，说的正是第二件事：规模很小时，系数和低阶项说了算；只有规模大起来，增长趋势才接管一切。

用大 O 记下增长

把上面的观察写成一个记号，就是大 O 记号（Big-O notation）这个记号最早由德国数学家巴赫曼（Paul Bachmann）在 1894 年引入，后来经朗道（Edmund Landau）推广开来；高德纳又把它带进算法分析，成为今天的通用写法。。它描述的是规模 n 趋于很大时，操作次数增长的上界。写法上有个约定：省略系数和低阶项，只留下增长最快的那一项。

3n + 5 = O(n), \qquad 2n^2 + 5n + 8 = O(n^2)

n 足够大时，低阶项占的份量越来越小，可以略去；系数不会变小，略去它，是因为它不改变增长的方式。

为什么可以像这样省？因为大 O 追问的是“n 变大以后谁说了算”。3n + 5 里，n 增大十倍，总次数也大致增大十倍；系数 3 让直线更陡，常数项 5 把它整体上移，但都不会改变它是一条直线。而 2n^2 + 5n + 8 里，平方项会迅速压过其余部分，决定形状的是 n^2。

四种常见的“长相”

先认一认四种最常见的增长：

常数时间

O(1)：一步到位。规模怎么变，操作次数都不变。

对数时间

O(\log n)：每轮砍掉一半。范围缩得飞快，曲线几乎是平的。

线性时间

O(n)：逐个查看。规模翻倍，工作量也翻倍。

平方时间

O(n^2)：两两组合。规模翻倍，工作量涨到四倍。

只记形状容易混，换成具体数字就直观了。同样处理 1000 个元素，结果列在里。

1000 个元素时，四种复杂度大约要做多少次基本操作
复杂度n = 1000 时本课程里的例子
O(1)1 次按下标直接读取数组中的元素
O(\log n)约 10 次有序数组的二分查找
O(n)1000 次扫描数组找最大值
O(n^2)1,000,000 次两两比较所有数对

写复杂度有两个动作不能省：先说清分析的是最好、平均还是最坏情况，再省略系数与低阶项。顺序查找最坏是 O(n)；“目标恰好在第一个”只是最好情况，不能拿它当一般结论。

动手数一次

最后一行的“两两比较所有数对”，可以用一段很短的程序来体会：检查一组数里有没有重复。

def has_duplicate(numbers):
    n = len(numbers)
    for i in range(n):
        for j in range(i + 1, n):
            if numbers[i] == numbers[j]:
                return True
    return False

把第 5 行的比较当作基本操作。最坏情况下（没有任何重复），n 个数一共要比较多少次？时间复杂度是多少？

解答

第一个数要和后面的 n - 1 个数各比一次，第二个数比 n - 2 次……最后一个数不用再比。加起来是

(n - 1) + (n - 2) + \cdots + 1 = \frac{n(n - 1)}{2}

展开得 \frac{1}{2}n^2 - \frac{1}{2}n，省略系数与低阶项，时间复杂度是 O(n^2)。n = 1000 时，给出 499,500 次，与表中的一百万次是同一个量级。

两种查找，差别有多大

把两种查找放进同一个问题里：数组有 n 个元素且已经有序，比较最坏情况下的工作量。二分查找的次数来自上一讲的，推导见。

顺序查找

  • 从第一个元素开始逐个比较
  • 最坏要看完全部 n 个元素
  • 时间复杂度 O(n)
  • 对数据顺序没有要求
  • 1,000,000 个元素最坏 1,000,000 次比较

二分查找

  • 每次比较后丢掉一半候选
  • 最坏比较 \lfloor \log_2 n \rfloor + 1 次
  • 时间复杂度 O(\log n)
  • 要求数据事先有序
  • 1,000,000 个元素最坏 20 次比较

20 与 1,000,000 相差五万倍。查一次，一百万次比较对今天的计算机也只是一眨眼；可同样的查找如果每秒要做上万次，差距就从“察觉不到”变成“等不起”。规模再涨十倍，顺序查找要多做十倍的工作，二分查找只多比较三四次。

别只算查找那一步。原始数据若无序，为了用二分查找先排序，排序本身通常要 O(n \log n)。只查一两次的话，准备成本可能高过直接顺序查找；只有当同一份有序数据要被反复查询，提前排序才真正划算。

数据库的“索引”就是这笔账的工业版本。建索引相当于提前把数据按某一列排好序：要花时间，也占空间；换来的是此后每一次按这一列查询，都不必再逐行扫描。

-- 没有索引：逐行扫描整张表，O(n)
SELECT name FROM students WHERE student_no = 20231;

-- 建立索引：数据库维护一份按 student_no 排序的结构
CREATE INDEX idx_student_no ON students (student_no);

-- 同一条查询，现在约 O(log n)
SELECT name FROM students WHERE student_no = 20231;

在 SQLite 里给查询加上 EXPLAIN QUERY PLAN，可以看到执行方式从 SCAN（逐行扫描）变成了 SEARCH … USING INDEX（按索引查找）。

这条路是怎么走过来的

把“效率”当成可以量化的学问，并不是一开始就有的想法。它经历了从“能不能算出来”到“要算多久”的转变，下面几个节点大致标出了这条路。

  1. 1936 图灵：先问“能不能算”。图灵用图灵机刻画“可计算”的含义。一个问题先要存在算法解，才谈得上快慢；这是后来复杂度理论的起点。
  2. 1965 埃德蒙兹：多项式时间算“有效”。Jack Edmonds 在研究图的匹配问题时提出，把“存在多项式时间的算法”作为问题算得上有效可解的判据。此后 P 类问题有了明确的直觉含义。
  3. 1971 库克：第一个 NP 完全问题。Stephen Cook 证明布尔可满足性问题（SAT）属于 NP，且所有 NP 问题都能在多项式时间内归约到它。从此“看起来难”有了严格的说法。
  4. 1972 卡普：21 个 NP 完全问题。Richard Karp 用归约把 NP 完全性扩展到 21 个实际问题，从图着色到背包。人们这才发现，难解问题不是零星特例，而是一大片P 是否等于 NP，至今仍无定论。它是克雷数学研究所七道“千禧年大奖难题”之一，悬赏一百万美元；如果某个 NP 完全问题被找到多项式时间算法，P 与 NP 就会相等。。

这些年份不需要背下来，它们留下的是两个习惯：拿到一个问题，先看它的工作量随规模怎样增长；再确认自己面对的是“相对容易”的一类，还是“公认困难”的一类，好决定是求精确解，还是接受一个够用的近似。

检查你的理解

用几道题检验刚才的三个结论：数操作、认增长、说清前提。

某算法在最坏情况下要做 2n^2 + 5n + 8 次基本操作，最贴近其增长阶的写法是？

  1. O(1)
  2. O(n)
  3. O(n^2)

n 足够大时，2n^2 这一项主导增长，5n 与常数项 8 都可以略去，因此常用写法是 O(n^2)。注意前提：这里说的是最坏情况下的增长阶。

一个 O(n^2) 的算法，数据量从 1000 增加到 2000，工作量大约变成原来的几倍？

把 n 换成 2n，看看 n^2 变成了什么。

(2n)^2 = 4n^2：规模翻倍，工作量变成四倍。

下面哪些说法是正确的？

  1. 复杂度更低的算法，在任何规模下都更快
  2. 大 O 记号省略系数与低阶项
  3. 顺序查找的时间复杂度是 O(1)，因为目标可能恰好在第一个
  4. 数据量足够大时，对数增长的算法终将比线性增长的算法做更少的操作

留意“任何规模”“可能恰好”这类字眼：它们说的是哪一种情况？

第二、四项正确。第一项错在“任何规模”：规模很小时，系数更小的算法可能反而更快。第三项把最好情况当成了一般结论，顺序查找最坏要看完全部元素，是 O(n)。

本讲小结

  • 用基本操作次数代替秒数，才能把机器差异从讨论里去掉。
  • 大 O 记录增长趋势：省略系数与低阶项，但要先说明最好、平均还是最坏情况。
  • \log n、n、n^2 在规模小时差距有限，规模一大就判若云泥。
  • 复杂度低不等于一定更快：准备数据的代价、被大 O 略去的系数，同样算成本。

最后一讲（）换一个方向：不再问“多快”，而是问“能不能把一个大问题，换成更小的同类问题”，让它借助更小的自己得到答案。
