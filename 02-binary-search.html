每次排除一半的可能

上一讲，我们靠逐张比较找到了最大值。如果数据已经从小到大排好，真的还需要一张一张看过去吗？猜数字的经验提示我们：不必。这一讲，我们把这种“每一步排除一半”的做法写成算法，并且一格一格地盯住边界。

  • 说清“有序”带来了什么信息
  • 画出每次比较后的区间变化
  • 写出闭区间的二分查找
  • 算出最多需要比较几次

从猜数字开始

朋友在 1 到 100 之间想了一个整数，你每次猜一个数，他只会回答三个词之一：大了、小了、猜对了。你会怎么猜？

从 1 开始逐个问当然可行：最坏问到第 100 个，一共 100 次。但如果先猜 50，无论答案是“大了”还是“小了”，都立刻排除掉一半：剩下的可能从 100 个变成 50 个。再猜剩下区间的中点，可能只剩 25 个……最多猜七次七次为什么够：每猜错一次，剩下的候选至多是原来的一半，依次是 50、25、12、6、3、1 个；猜错六次之后只剩一个数，第七次必中。也可以这样算：2^7 = 128 \gt 100。，就一定能猜中。

这就是二分查找（binary search）的核心：每次比较之后，保留下来的候选范围至少缩小一半。它成立的关键条件只有一个——候选数据是有序的。只有排好队，“比中间值大”才能推出“答案在右边”。真正省时间的，不是动作更快，而是方向更准。

二分查找不能用在无序数组上。数据乱序时，中间值是 9 并不能说明比 9 大的数都在右边——它可能出现在任何位置。此时“排除一半”的推理直接失效，程序往往不报错，只是安静地给出错误答案。

让区间不断收窄

把可能的范围用一个左端点和一个右端点框起来，记作 [left, right]，意思是“答案可能在这两个位置之间（含端点）”。开始时整条数组都在框里；每比较一次，框就缩小一些。

以有序数组 [1, 3, 5, 7, 9, 11, 13, 15] 中找 13 为例：中点在下标 3（值是 7），13 比 7 大，于是丢掉中点以及它左边的全部，范围缩成下标 4 到 7；再取中点下标 5（值是 11），13 仍比 11 大，范围缩成下标 6 到 7；中点下标 6 正好是 13，比较结束。八个数，只比较了三次。

如果不利用顺序，从头一个一个看过去，要到第七次才碰到 13。与把两种走法并排画了出来。

注意每次排除之后端点怎么变：要么左端移到中点右边一格，要么右端移到中点左边一格。这个“加一 / 减一”看似琐碎，却是循环能够停下来的关键——中点已经比较过了，绝不能再留在候选区间里。

如果目标根本不在数组里，比如在上面的数组里找 6，区间会怎样变化？它最终停在哪一步、又该给出什么结果？先自己推一遍，再用的演示验证。

把区间写进代码

用两个变量表示闭区间的两端。只要 left <= right，框里就还有候选；当 left 超过 right，说明已经无路可走，目标不存在。上一讲说过，同一种算法可以写成不同语言的程序：下面给出三种语言的写法，切换选项卡即可对照，它们的逻辑完全一样。

def binary_search(numbers, target):
    left, right = 0, len(numbers) - 1

    while left <= right:
        middle = left + (right - left) // 2
        if numbers[middle] == target:
            return middle
        if numbers[middle] < target:
            left = middle + 1
        else:
            right = middle - 1

    return -1  # 目标不在数组中

print(binary_search([1, 3, 5, 7, 9, 11, 13, 15], 13))  # 6
function binarySearch(numbers, target) {
  let left = 0;
  let right = numbers.length - 1;

  while (left <= right) {
    const middle = left + Math.floor((right - left) / 2);
    if (numbers[middle] === target) return middle;
    if (numbers[middle] < target) left = middle + 1;
    else right = middle - 1;
  }

  return -1; // 目标不在数组中
}

console.log(binarySearch([1, 3, 5, 7, 9, 11, 13, 15], 13)); // 6
#include <stdio.h>

int binary_search(const int numbers[], int length, int target) {
  int left = 0;
  int right = length - 1;

  while (left <= right) {
    int middle = left + (right - left) / 2;
    if (numbers[middle] == target) return middle;
    if (numbers[middle] < target) left = middle + 1;
    else right = middle - 1;
  }

  return -1; // 目标不在数组中
}

int main(void) {
  int numbers[] = {1, 3, 5, 7, 9, 11, 13, 15};
  printf("%d\n", binary_search(numbers, 8, 13)); // 6
  return 0;
}

返回的是目标的下标（从 0 开始数），不是目标的数值；三种语言的下标都从 0 开始。

二分查找的基本思想相对简单，细节却出人意料地微妙。

高德纳《计算机程序设计艺术》卷 3

最微妙的一处，是计算中点的那一行。C 版里它是这样写的：

int middle = left + (right - left) / 2;

它没有写成更直观的 (left + right) / 2。在 Python 里两种写法结果完全一样，因为 Python 的整数没有上限；但 C、Java 这类语言的整数位数是固定的，两个很大的下标相加，可能超出整数能表示的范围。先算差、再折半，就没有这个问题，是个值得早点养成的习惯。这不是纸上谈兵：Java 标准库的二分查找就曾经写成 (low + high) / 2，这个错误潜伏了大约九年，直到 2006 年才被修复见 Joshua Bloch 2006 年的文章《Extra, Extra - Read All About It: Nearly All Binary Searches and Mergesorts are Broken》。他正是那段库代码的作者。。

在整数位数固定的语言里，left + right 一旦溢出，结果通常是一个负数；拿它当下标，等于访问数组之外的内存：Java 会抛出异常，C 则可能读到无关的数据，甚至直接崩溃。数组不够大时，测试永远发现不了它——所以要靠写法，而不是靠运气。

如果把循环条件写成 left < right，会怎样？

区间只剩一个元素时，left 等于 right，循环提前结束，最后这个候选根本没有被比较。在上面的数组里找 15：区间一路缩到只剩下标 7，程序却直接返回 −1。闭区间的写法里，“还有候选”的意思是 left <= right，等号不能丢。

手写二分查找是面试里的常客，考的就是三处边界：循环条件用 <=，左端更新成 middle + 1，右端更新成 middle - 1。这三处与“闭区间”的约定是配套的，只改其中一处，程序就会漏掉元素，或者停不下来。

实际写程序时不必每次手写：Python 标准库的 bisect 模块已经实现了二分查找。先亲手写一遍，是为了看懂它替你处理了哪些边界。

亲手缩小搜索区间

下面两段演示用的是同一个数组：第一段查找数组里有的 13，第二段查找并不存在的 6。点“下一步”逐轮观察：“左”“右”标出当前区间的两端，“中”是这一轮比较的中点。

观察两件事。第一，每轮被排除的格子越来越多。第二，中点落在当前区间的中间；区间里的位置是偶数个时，没有正中间，取的是靠左的那一个（第 1 轮的 8 个位置里，取的是第 4 个）。候选区间变空的那一步，就是“没有找到”。

算一算：最多几次

演示只能让我们看到个别情况。“最多几次”需要另外算——这也是算法课上最常被考的一类推理。

在 8 个元素的有序数组里做二分查找，最多需要比较几次，才能断定目标不存在？

先想清楚“最多”是对谁而言：数组有 8 个位置，每一种目标（包括不存在的目标）都会走出一条比较路径，我们要找的是所有这些路径里最长的一条。可以先按“每次把区间长度减半”来数。

解答

每比较一次，区间长度至多变成原来的一半，最长的那条路径上依次是 8、4、2、1。区间长度为 8、4、2、1 时各比较一次，一共 4 次；第 4 次比较之后区间变空，就能断定目标不存在。

把数字换大一点，结论会更有分量：1024 个元素最多 11 次，1,000,000 个元素最多 20 次。而顺序查找在这两种规模下，最坏分别要看 1024 个和 1,000,000 个位置。

把的数法写成公式：n 个元素的闭区间二分查找，最坏情况下的比较次数是

C(n) = \lfloor \log_2 n \rfloor + 1

其中 \lfloor x \rfloor 表示把 x 向下取整。代入 n = 8，得到 \lfloor \log_2 8 \rfloor + 1 = 3 + 1 = 4，与上面的数法一致。还说明了一件事：元素个数翻一倍，比较次数只多一次。

检查你的理解

二分查找能一次排除大量元素，最根本的原因是什么？

  1. 数据有序，一次比较就能确定目标在哪一侧
  2. 每次都从正中间开始比较
  3. 数组的长度正好是 2 的整数次幂

二分查找能一次排除大量候选，靠的是数据有序：中间值比目标小，就能同时排除中点以及它左边的全部元素。无序数据没有这个性质，“排除一半”的推理也就不成立。取中点只决定一次排除多少；长度是不是 2 的整数次幂，只影响能不能恰好对半分。

下面哪些数据可以直接使用二分查找？

  1. 按学号从小到大排好的名单
  2. 按到店先后记下的顾客手机号
  3. 按拼音顺序编排的词典
  4. 刚洗过的一副扑克牌

逐项问一句：看到中间那一项之后，能不能断定目标在它的哪一侧？

名单和词典都按查找用的那个键排好了序，可以直接二分。手机号是按到店时间记的，就号码本身而言是乱序；洗过的牌没有任何顺序。这两种情况只能先排序，或者逐个查找。

把猜数字的范围扩大到 1 到 1000，用二分的办法最多要猜几次？

回想例题里的数法：区间长度从 1000 开始，每猜一次减半，依次是 1000、500、250……一直数到 1，一共有几个数？

\lfloor \log_2 1000 \rfloor + 1 = 9 + 1 = 10。也可以这样想：每猜错一次，候选至多剩下一半；2^{10} = 1024 \gt 1000，所以猜错九次之后至多只剩一个数，第十次必中。

带走一个习惯：在动手逐个尝试之前，先问自己——这个问题里有哪些条件，能帮我一次排除一大批可能？

本讲小结

  • 二分查找的前提是有序：没有顺序，“排除一半”的推理就不成立。
  • 用闭区间 [left, right] 表示候选范围，比较后把端点移到中点的旁边（middle + 1 或 middle - 1），区间必然缩小。
  • n 个元素最多比较 \lfloor \log_2 n \rfloor + 1 次；1024 个元素只需要 11 次。
